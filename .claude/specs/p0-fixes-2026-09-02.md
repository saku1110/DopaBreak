### A-1. 🔴4 宣言した時間の中で開き直したら一呼吸を出さず通す

現状: `recordCatalogOpen` は `persist(idleState(at:))`（`InterventionEngine.swift:194`）で idle に戻し `.temporarilyAllowed` を作らない。`AppContainer.consumeInterventionRequest`（`:1009-1014`）の `reshieldIfExpired` ＋ `hasActiveTemporaryAllowance` は恒久 false。結果、10分と決めた中でSNSを開き直すたび一呼吸がフル再発し、AttemptLog(opened) と ReflectionLog が毎回増える。

方針: **状態機械は触らない**。カタログ経路専用の許可ストアを足す。

Core 新規 `Storage/CatalogAllowanceStore.swift`（App Group の UserDefaults。`SettingsStore` と同じ suite）
```swift
public final class CatalogAllowanceStore {
    public func grant(catalogID: String, until: Date)
    public func activeAllowance(catalogID: String, at now: Date) -> Date?   // until > now のときだけ
    public func revoke(catalogID: String)
    public func purgeExpired(at now: Date)
}
```
- `InterventionFlowModel.recordCatalogOpen(for:)`（`:322-335`）: `engine.recordCatalogOpen` の戻り `ReflectionLog.promptedAt` を `until` として `grant`。振り返り通知の予約はそのまま

- **通す画面**: `InterventionTarget` またはフロー開始パラメータに「通過モード（until）」を持たせ、`InterventionFlowModel.start()` が通過モードなら `stage = .passingThrough(remainingMinutes:)` にして 0.6秒後に `openCatalogTarget` と同じURL起動を行う（**記録しない**: AttemptLog・ReflectionLog・許可の再付与・振り返り通知の再予約はすべて無し）。表示は既存 `openingScreen` と同じ骨格で、タイトル `intervention.pass_through.title`「{App}を開きます」・副題 `intervention.pass_through.remaining`「決めた時間はあと{N}分」。URL起動失敗時は既存の `manual_fallback` と同じ案内
- 対象アプリから外したとき（`setTargetCatalogIDs`）とクランプ時に `revoke`。前面復帰の `refresh()` で `purgeExpired`
- FunnelEvent 追加: `interventionPassThrough = "intervention_pass_through"`

### A-6. 実機バグ: 振り返り通知をタップするとDopaBreakが一瞬開いてSNSに戻る（2026-09-02 19:55・オーナー報告「DopaBreakが開かなかった」）

端末の痕跡: プロセス生存・SplashBoardスナップショットと App Group plist が 19:55 に更新・`pendingNotificationDestination` は消費済み。＝タップで前面に来た直後に裏へ回った。
機構（Opus5調査で確定）: 前面復帰の `RootTabView.handleAppActive`（`:368-382`）で、振り返りの宛先を消費してシートを予約した直後に `checkPendingIntervention` が**古い通過（pass-through）要求**を拾い、`presentPendingInterventionIfValid` が `.dismissReflection` で振り返りを捨てて通過画面を出し、SNSのURLを開いて裏へ回る。古い要求の出どころは2つ: ①通過画面は `open` 後に `onFinished` を自分で呼ばず、500ms後の dismissal task 任せなので、背面移行中に走らず `pendingInterventionTarget` が残る ②DopaBreak自身がSNSのURLを開いた直後にショートカットの自動化（`StartInterventionIntent`・`openAppWhenRun = true`）が再発火して `pendingStartInterventionCatalogID` を書き残す。さらに通過対象は `until` の期限切れを検査していない（`RootTabView.swift:527-539`）ため、期限切れでも「あと1分」で再提示する。

修正（4点すべて入れる。1つでも欠けると別経路で再発する）:

1. **通過は開いた瞬間に要求を消す**: `InterventionFlowModel.beginPassThrough`（`:403-427`）で `UIApplication.shared.open` の completion（成功・失敗とも）で `model.discardPendingInterventionTarget(ifMatching: target)` を呼ぶ。通常の `.opening` 経路（`:369-399`）も同様に completion で discard する（overlay の表示は既存の `onFinished` 経路で閉じる）
2. **期限切れの通過要求は再提示しない**: `RootTabView.presentPendingInterventionIfValid` で `.catalogPassThrough(_, until:)` の `until <= Date()` は非対象と同じ分岐（discard＋アニメなし dismiss）。`RootTabView.initialTarget`（`:108-112`）も同じ検査を通す
3. **自動化の起動要求に鮮度と自己起動除外を持たせる**:
   - `SettingsStore` に `pendingStartInterventionRequestedAt: Date?` と `lastSelfOpenedCatalogID: String?` / `lastSelfOpenedAt: Date?` を追加（App Group）
   - `StartInterventionIntent.perform`（`:85-98`）は要求と同時に `pendingStartInterventionRequestedAt = Date()` を書く
   - `InterventionFlowModel` がSNSのURLを開く直前（通常・通過の両方）に `lastSelfOpenedCatalogID/At` を書く
   - Core 新規 `Services/AutomationRequestPolicy.swift`（純粋関数）: `decision(requestedCatalogID:requestedAt:now:lastSelfOpenedCatalogID:lastSelfOpenedAt:) -> .consume | .discardStale | .discardSelfOpen`。`requestedAt` が nil または `now - requestedAt > 60秒` → `.discardStale`／同じ catalogID で `now - lastSelfOpenedAt < 20秒` → `.discardSelfOpen`／それ以外 `.consume`
   - `AppModel.consumePendingInterventionRequest`（`:1011-1030`）と `consumeAutomationVerificationOnly` はこの判定を通し、discard のときは要求をクリアして何もしない（介入・通過・非対象シートのいずれも出さない）。FunnelEvent `automationRequestDiscarded = "automation_request_discarded"`（detail に stale / self_open）。**検収マークは discard でも行う**（自動化が動いた事実は残す）
4. **振り返りの宛先が有効なら通過より優先**: `RootTabView.handleAppActive` で `settingsStore.pendingNotificationDestination` が有効かつ `.reflection` のときは、`checkPendingIntervention` が通過候補（許可が有効な要求）を拾っても通過を出さず要求を捨てる（`AppModel.consumeInterventionRequest` に `suppressPassThrough: Bool` を渡す形でよい）。自動化の本物の起動（許可が無い＝一呼吸が必要）は従来どおり最優先

テスト: Core `AutomationRequestPolicyTests`（鮮度60秒の境界／自己起動20秒の境界／別アプリは consume）。アプリ側 `InterventionRoutingTests` に「通過→open completion で pendingInterventionTarget が nil」「期限切れ通過は再提示されない」「reflection 宛先が有効なとき通過候補は捨てられる」を追加。全テスト失敗0・lint 2本 exit 0。

## 🔴10 について（コード変更なし・実機確認項目）

シールドが張られているアプリはアイコンをタップしてもiOSのシールド画面が出るだけで**起動しない**。ショートカットの「開いている」トリガーは起動を条件にするため、完全ブロック中のアプリでは自動化は発火しないはず。従って「窓の中で一呼吸フルコース→最後にシールドの壁」は起きない見込み。
- 実機確認: 夜だけ強化の窓の中で、完全ブロック対象かつ一呼吸対象でもあるアプリをタップし、①シールドだけ出て自動化が発火しないこと ②発火してしまう場合はその旨を報告（その場合のみ、介入の `.opening` 段階でブロック中の案内を出す追加設計を起こす）
- `device-verification-runbook.md` に上記を1項目追加する（バッチCで）

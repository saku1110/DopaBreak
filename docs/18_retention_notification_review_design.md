## 1. レビュー誘導設計（新規・P1）

### 方針

- API: SwiftUI `@Environment(\.requestReview)`（StoreKit・deployment target 17.0でそのまま使える）。独自ダイアログ・ストア直接遷移は使わない
- **満足度ゲート禁止**（「満足ですか？」→はいの人だけ、はポリシー違反リスク）。代わりに「発火条件を成果の実績値でゲート」する＝不満ユーザーは条件に達しにくい構造で品質を担保する
- 不満の受け皿: 設定に「フィードバックを送る」（mailto）を同時実装し、レビュー依頼とは完全に切り離す

### 発火タイミング

**唯一のトリガー: 勝ち画面（`InterventionFlowModel` stage `.win`）表示から1.5秒後。**

理由: DopaBreakの成果ピークは「開かずに戻れた」瞬間そのもの。勝ち画面はユーザーが達成を確認する静止画面で、次の操作を急かされない。起動直後・介入判断中・失敗画面では出さない。

### 発火条件（全て満たす場合のみ）

`ReviewPromptPolicy`（DopaBreakCore・純粋ロジック・100%テスト）:

| 条件 | 値 | 理由 |
|------|-----|------|
| 累計「開かなかった」回数 | ≥ 5回（`StatsService.cancelledAttemptsAllTime()`） | 成果の実感が確立してから |
| 初回起動からの経過 | ≥ 3日 | 初回起動直後の禁止（規則B-1） |
| 前回表示からの間隔 | ≥ 90日 | 自前制御（OS年3回制限とは独立に持つ） |
| 直近365日の表示回数 | < 3回 | OSの年3回上限に整合 |
| 今回セッションの文脈 | 介入スキップ直後でない・購入/復元の失敗直後でない | 失敗体験直後の禁止（規則B-1） |

### 永続化・計測

- `SettingsStore` 新キー: `reviewPromptEventDates: [Date]`（表示日時の配列・365日より古いものは刈り取り）
- `FunnelEventStore` に `review_prompt_shown` イベント追加（表示回数と後日のレビュー数推移を照合するため）
- 注意: `requestReview` はOS判断で実際には出ないことがある。**「呼び出した事実」を記録**し、実際に出たかは関知しない（APIが結果を返さない仕様）

### 実機検証（規則B-1）

Sandbox/開発ビルドでは毎回表示される仕様を利用し、条件を満たした勝ち画面で実際にダイアログが出ることを実機確認してから✅とする。

## 3. 利用時間ウォッチ（介入なしの時間超過警告・オーナー依頼 2026-08-11）

### 何ができるか（技術確定）

**「対象アプリを合計N時間使ったら警告通知」はiOS公式APIで実現可能。** DeviceActivityフレームワークの閾値イベントを使う。

- `DeviceActivityEvent(threshold:)` に対象アプリ群と累積時間を登録すると、**その日の合計利用が閾値に達した瞬間**にMonitor Extensionへコールバックが来る
- Extensionから直接ローカル通知を送れる（**アプリを起動していなくても動く**。one sec/Opalと同方式）
- ショートカットのオートメーションとは独立して動くため、**オートメーション未設定・すり抜けユーザーにも届く**（既知制約「Shortcuts側すり抜け」の穴をここで塞げる）

### 資産の現状（実査 2026-08-11）

| 必要要素 | 状態 |
|---------|------|
| FamilyControls Distribution entitlement | ✅ 承認済み（2026-07-03・4 App ID有効化済み） |
| MonitorExtensionターゲット＋entitlements | ✅ 存在（スケルトンのみ・中身は空実装） |
| スクリーンタイム許可導線（Settings） | ✅ 実装済み（shield配線 (3)-(6) の遺産） |
| FamilyActivityPicker＋選択の永続化 | ✅ ScreenTimeCenter実装済み |
| `startMonitoring` 呼び出し＋閾値イベント | ❌ 未実装（今回の実装範囲） |
| Extension内の通知送信 | ❌ 未実装（今回の実装範囲） |

新規ターゲット追加は不要。**実装範囲は「スケジュール登録＋Extension内のコールバック→通知」のみ**で、v1.1送りにしたshieldコードの資産をほぼ流用できる。

### 設計の軸（オーナー問い「利用量か時間帯か」への回答）

**主軸は利用量。時間帯は修飾子として使う。**

- 時間帯単体をトリガーにすると、同じ1時間でも文脈（休日の昼と平日深夜）で正邪が分かれ誤爆する。誤爆1回の代償は通知オフ＝この機能の全損
- 利用量（連続・累積）は「いま起きている行動そのもの」なので誤爆しない
- 時間帯はProの夜間モード（就寝前だけ問いの間隔を詰める）として重ねる。既存の起床/就寝時刻設定（`wakeTimeMinutes`/`bedTimeMinutes`・モノクロ機能で実装済み）をそのまま流用できる

### 統一メカニズム（1本の仕組みで両プランを賄う）

DeviceActivityに「連続利用時間」を直接測るAPIはない。そこで**15分刻みの累積閾値イベントの梯子**（15分/30分/45分…最大6時間まで）を1本登録し、両プランで共用する:

1. Extensionは各段の発火時刻をApp Groupへ記録するだけ（メモリ上限対策・ロジック最小）
2. **Pro**: 各段の発火＝そのまま問いかけ通知（下記ガード付き）
3. **Free**: 発火間隔から連続性を推定する。直前の段から約20分以内に次の段が発火し続けていれば「連続利用中」とみなし、連続ランが閾値に達した時点で1回だけ警告
4. 副産物: 発火ログがそのまま利用タイムラインになり、将来Statsで「今日いつ・どれだけ見たか」を出せる

精度の正直な申告: 連続判定は15分刻みの近似で誤差±15分程度。OSの集計遅延も数分ある。「2時間ちょうど」の保証はできないが、この用途には十分。

### なぜ「過去のスクリーンタイム」から計算しないのか（オーナー質問への回答 2026-08-11）

iOSのスクリーンタイムデータへのアプリのアクセスは、Appleがプライバシー設計で2系統に分離している:

| API | できること | できないこと |
|-----|-----------|-------------|
| DeviceActivityReport | 過去の利用時間を**表示する**（専用のサンドボックス化されたUIエクステンション内でのみ描画） | **アプリ本体は数値を一切読めない**。データはエクステンションの外に出せず、ロジック・通知・推計・保存・送信に使えない |
| DeviceActivityMonitor（本設計の方式） | 利用が閾値に達した瞬間のコールバック（リアルタイム） | 過去データの照会。「昨日何時間使ったか」は取得不可 |

- つまり「過去のスクリーンタイムから利用時間を計算」はAppleの設計上**どのアプリにも不可能**（one sec/Opalも同じ制約下にある）。オンボの推計が自己申告（Q1）なのはこのため
- 通知の発火判定に使えるのはMonitorの閾値イベントのみ。本設計の15分梯子方式が唯一の実現手段
- **副次機会（P3候補）**: Reportエクステンションを追加すれば、Statsタブに「実測の利用時間グラフ」を埋め込み表示できる（表示のみ・数値はロジックに使えない）。実測が減っていく様子を見せられれば解約防止に効くため、利用時間ウォッチ実装後の拡張として検討する

### 制約（実装前に了解しておく事項）

- 発火は閾値到達から数分遅れることがある（OSの集計タイミング依存）。連続判定は15分刻みの近似で誤差±15分程度
- シミュレータでは動かない。**実機検証必須**
- Extensionのメモリ上限が小さい（約6MB）。Extension内は「時刻記録＋通知送信」のみに絞り、判定ロジックはCoreの純粋関数（`UsageWatchPolicy`）としてテスト可能にする
- 閾値イベントの登録本数上限は公表仕様が曖昧なため、実機で梯子の最大段数（6時間=24段を想定）を検証してから確定する

## 4. 解約率低減設計（オーナー依頼 2026-08-11）

「必ず低くなる」ことは事前保証できないため、**解約の主要因を1つずつ設計で塞ぎ、計測で検証する**構成にする。過度な引き止め（解約妨害UI）は審査違反かつ信頼毀損のため採用しない。

### 解約要因→対策マップ

| 解約要因 | 対策 | 状態 |
|---------|------|------|
| 効果を実感できない（最大要因） | **利用時間ウォッチ（§3）**: オートメーション未設定・すり抜けユーザーにも毎日価値が届く | 新規 |
| 成果が見えない・忘れる | **月次レポートの恒常化**: 現在は購入+30日の1回きり → **毎月配信**へ変更（開かなかった回数＋取り戻した推計時間を毎月可視化＝保有効果の更新） | 是正 |
| 習慣が切れて離脱 | **炎ステージ昇格通知**: 3日/7日/21日(青い炎)到達時に祝福通知。ストリーク＝解約の心理コスト化。降格を脅しに使わない（火は消えない仕様を維持） | 新規（炎ステージ実装とセット） |
| 月額の毎月の解約機会 | **年額移行オファー**: 月額課金3ヶ月目に実績サマリー付きで年額提案を1回だけ通知（年額比率↑＝解約機会が年1回に減る。SOSA裏付けあり） | 新規 |
| 解約意図の放置 | **解約検知→セーブ通知**: `willAutoRenew`がfalseへ変化したら、期限3日前に実績＋「青い炎まであとN日」を**1回だけ**通知。あわせてwin-backオファー（ASC設定・preflightブロッカー⑥） | 新規 |
| 請求失敗の無言解約（非自発チャーン） | ASCで**Billing Grace Period有効化**（設定作業のみ・A-5のクライアント側は実装済み） | ASC作業 |
| 更新時の不意打ち感 | 12ヶ月更新予告（実装済み）＋トライアル終了2日前予告（実装済み）を維持 | ✅済 |

### ⚠️ 月次レポート「恒常化」の現状の制約（2026-08-11 監査で判明・**オーナー判断待ち**）

現在の実装（`RetentionNotificationDateCalculator.nextMonthlyReportDate` → `LockSurfaceCoordinator`）は、**次の1回分だけ**を非反復の`UNCalendarNotificationTrigger`で予約する。翌々月分はアプリがもう一度起動されたときに初めて積まれる。

- 結果: **アプリを開かなくなった購読者には、次の1回が届いた後は何も届かない**（2ヶ月目に離脱したユーザーには3ヶ月目のレポートだけが届き、4・5・6ヶ月目は無音）
- これは §4 が「解約防止の主柱」と位置づけた対象＝まさに離れかけている人に届かないことを意味する
- `AppContainer` の既存コメント（trailing-month summary の鮮度）が扱っているのは**件数の鮮度**であって、この非反復の話ではない

**選択肢（実装前にオーナー判断が必要）**

| 案 | 内容 | 代償 |
|----|------|------|
| A | 別識別子で `DateComponents(day:hour:minute:)` の**反復トリガー**を追加登録する | 反復通知の本文は後から差し替えられないため、**件数を含まない固定文**にするしかない（「今月のふりかえりができます」等）。件数入りの現行1回きり通知と併存させるか置き換えるかも判断が要る |
| B | 現状維持とし、この制約を仕様として明記する | 休眠者には届かない。§3 の利用時間ウォッチが実質の代替になるかを計測で確認する |

判断が出るまでコードは変更しない。

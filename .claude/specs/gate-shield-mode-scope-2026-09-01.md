# 常時ゲートをモードで絞る（時間制御を機能させる）— 設計（2026-09-01）

オーナー報告（2026-09-01）:
- 「なんで時間制御もしてないのにSNSアイコンがグレーアウトして砂時計マークついてる？」
- 「スクリーンタイム許可したら常にアプリ開けなくなってる。**時間制御の意味とか全くないじゃん**」
- 先行指示:「A。ただ**スクリーンタイムの時間制御外の時は普通の一呼吸**」

---

## 1. 本丸のバグ: ゲートがモードを見ていない

`ios/DopaBreak/GateShieldController.swift` の `prepareSelection()`:

```swift
let selectionDataList = try ruleStore.enabledRules()   // ← mode で絞っていない
    .map(\.activitySelectionData)
    .filter { !$0.isEmpty }
```

**有効なルール全部**を常時シールドの対象にしている。`TargetRule.mode` を一切見ていない。

結果:
- 「夜だけ強化」を選んでも、夜以外の時間もシールドがかかり続ける
- 「ディープフォーカス」を選んでも、窓の外でシールドが残る
- SNSアイコンが24時間グレーアウト＋砂時計になり、**時間帯の設定が無意味になる**

`ShieldController.applyShield` のほうは `rule.mode == .deepFocus && isDeepFocusWindowActive` /
`rule.mode == .nightOnly && isNightWindow` と正しく窓で絞っている。
**時間窓の実装は正しく、常時ゲートだけがモードを無視している。**

### 修正

`prepareSelection()` の対象を **`mode == .standard` のルールだけ**に絞る。

```swift
let selectionDataList = try ruleStore.enabledRules()
    .filter { $0.mode == .standard }
    .map(\.activitySelectionData)
    .filter { !$0.isEmpty }
```

判定は Core 側の純関数へ切り出してテストできる形にすること
（例: `GateShieldScope.selectionData(from:)`）。`GateShieldController` はそれを呼ぶだけにする。

### 各モードの期待挙動（修正後）

| モード | 窓の外 | 窓の中 |
|---|---|---|
| 標準 | **常にシールド**。シールドが一呼吸の入口。アイコンはグレー＋砂時計（スクリーンタイムで起動を捕まえる以上、これは避けられない） | 同左 |
| 夜だけ強化 | **シールドなし**。アイコンは通常。ショートカット自動化があれば普通の一呼吸 | 完全ブロック（通過不可） |
| ディープフォーカス | **シールドなし**。同上 | 完全ブロック（通過不可） |

これで「時間制御外は普通の一呼吸」が成立する。

### 移行時の後始末
既に `nightOnly` / `deepFocus` のルールで張られている常時ゲートのシールドは、
この修正後の最初の同期で**必ず剥がれること**。剥がれ残ると窓の外でも開けないままになる。
`GateShieldController.sync` の `.apply` 経路が、対象が空になったときに確実に解除することを確認し、
テストで守ること。

## 2. catalog介入の抑止をモード連動にする

`AppModel.isScreenTimeGateConfigured` は現在「有効ルールに選択データがあるか」で判定している。
これも **`mode == .standard` のルールだけ**を見るように直す。

理由: 夜だけ強化・ディープフォーカスのユーザーは、窓の外では常時ゲートが無い。
そこで catalog（ショートカット自動化）の一呼吸を止めてしまうと、**一呼吸が一切効かなくなる**。

修正後の意味は「**このユーザーは標準モードでスクリーンタイムのゲートを使っている**」になる。

---

## 3. 行き止まりの解消（私の設計ミス）

現在、ゲート設定ありで `.catalog` 要求が来ると**何も出さずに捨てている**。
ショートカット自動化が発火してDopaBreakが前面に出るため、
ユーザーは**説明のないホーム画面**に着地する（オーナー報告「SNS開いたらアプリのホーム画面に飛ぶだけ」）。

捨てるのは維持しつつ、**自動化案内（`AutomationGuideView`）を提示する**。
③で「スクリーンタイムが入口。ショートカットは削除してよい」の内容に切り替え済みなので、それを出す。

制約:
- 前面復帰ごとに**最大1回**。ループ・積み重ねをしない
- `.gateToken` 介入 / ペイウォール / ロック画面確認 / child modal を**絶対に押しのけない**。
  既存の提示優先度ガードを再利用する
- 閉じられること。通常利用を妨げないこと
- 捨てた要求で attempt / open を記録しない
- `.catalog` 要求が実際に来たときだけ出す

---

## 4. 危険な副作用の確認（必須）

`.catalog` を捨てるときに `model.pendingInterventionTarget = nil` を実行している。
**シールドの「DopaBreakで開く」から来た `.gateToken` 要求と競合した場合、
gateToken を巻き込んで消していないか**を確認し、消しているなら直すこと。

シールド経由の要求が消えると、ユーザーはシールドを通過する手段を失い、
**対象アプリが一切開けなくなる**（オーナー報告「常にアプリ開けなくなってる」に一致しうる）。
両方の要求が同時に届く順序を変えたテストを追加すること。

---

## 受け入れ条件
- 夜だけ強化・ディープフォーカスを選ぶと、**窓の外ではアイコンがグレーアウトしない**
- 窓の外では従来どおり普通の一呼吸が出る
- 標準モードでは従来どおりシールドが入口になる
- 既存の張りっぱなしシールドが、修正後の初回同期で剥がれる
- `.catalog` 抑止時に説明のない行き止まりが発生しない
- `.gateToken` 要求が `.catalog` の破棄に巻き込まれない

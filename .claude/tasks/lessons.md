# Lessons（修正パターン・学びの蓄積）

## 2026-07-25 — 新規成果物の前に既存調査を必ず読む

**症状**: 3市場ローンチのASO（docs/16）とアプリ内ko/en翻訳を、既存の国別訴求調査を読まずに新規作成。日本語版の直訳になり、韓国向けに検証で否定済みの「디톡스」訴求を提案しかけた（オーナー指摘で発覚）。

**根本原因**: `output/audits/onboarding-copy-strategy-by-country-2026-07-17.md`（v2.1・WebSearch検証済み・146エージェント確定）という国別訴求の正本が既にあったのに、着手前に探索しなかった。

**教訓**:
- コピー/訴求/マーケ系の成果物を作る前に、必ず `output/audits/` `docs/02b` `docs/09` `docs/13` と design-decisions.md を先に読む。
- 特に「トランスクリエーション（各国訴求）」は直訳と別物。既存の検証済み戦略があれば**再生成せず適用**する。
- WebSearch検証済みの知見（例: KRで「디톡스」は懐疑報道でトレンド落ち・US「break the loop」は競合飽和）はスキルの一般論より優先度が高い。スキルだけで訴求を決めない。

**恒久対策**: 訴求/コピー作業のワークフローは「①既存監査・設計書を読む → ②不足分だけ調査 → ③適用 → ④QA」の順で開始する。

## 2026-07-25 (2) — 実装発明コピーの正本迂回と「機械的UI」誤分類（オーナー最終チェックで却下）

**症状**: Home目標カード「SNSの先ではなく、戻りたい先を決める」・目標空状態「戻りたい自分を決める／連れ戻す錨」がオーナー却下。意味不明・アフォーダンス不明・AI読点。3言語に直訳拡散済みだった。

**根本原因（3連鎖）**:
1. **実装時発明コピーがdocs/11正本を経由せず混入**（7/11-12・grep で正本に不存在を確認）
2. i18n抽出が「日本語を変えるな」の指示で悪文を忠実に正典化
3. トランスクリエーション対象の選定で Home/Goals の空状態・fallback を「機械的UI」に誤分類 → 訴求品質チェックを通らず直訳

**教訓**:
- **空状態・fallback・placeholder は訴求キー扱い**（ユーザーが最初に見る営業コピー。機械的UIではない）
- 原文（ja）自体を疑う工程を翻訳パイプラインに入れる。「原文に忠実」は原文が正本承認済みの場合のみ正しい
- 表示コピーの句読点は機械チェックで防ぐ → `scripts/lint-display-copy.py` 新設（doc11変更手順に組込済み）
- 空状態の原則: **詩でなくアフォーダンス**。「何ができる欄か」を1秒で伝える。比喩・気取った語彙は使わない

## 2026-08-06 — `git checkout --` で未コミット作業を破壊（自損・復旧済み）

**症状**: `Localizable.xcstrings` の1文字列を差し替える際、python で全体を再シリアライズしたら整形差分が3,499行に膨れた。「戻して surgical edit に切り替える」つもりで `git checkout -- ios/DopaBreak/Localizable.xcstrings` を実行し、**自分の変更だけでなく他セッションの未コミット変更（新規24キー・ja値50件・ko全463件の翻訳・en複数形5件）を全て破棄**した。

**根本原因**:
1. `git checkout -- <path>` は「直前の自分の編集を取り消す」コマンドではなく、**worktree を index の内容で上書きする**。対象ファイルに先行の未コミット変更がある場合、それも道連れになる
2. 作業前に `git status` で ` M`（未コミット変更あり）を認識していたのに、取り消し手段の選定でそれを考慮しなかった
3. JSONの全体再シリアライズを、整形が一致する確証を取る前に実行した（HEAD版は**キー未ソート**＝挿入順保持だったため `sort_keys=True` で全行が動いた）

**復旧手段（同種事故が起きたら同じ順で試す）**:
1. `git diff --cached`（index が HEAD より新しくないか）→ 今回は index==HEAD で不発
2. `git fsck --lost-found` の dangling blob → 不発（stage も commit もされていなかった）
3. VSCode ローカル履歴 `~/Library/Application Support/Code/User/History` → 本環境は未生成
4. `tmutil listlocalsnapshots /` → なし
5. **✅ ビルド成果物からの再構築** — `DerivedData/.../<lang>.lproj/Localizable.strings` と `Localizable.stringsdict` に全キー・全ロケールの値が残っていた。これが唯一の生存経路だった

**恒久対策**:
- **未コミット変更のあるファイルを触る前に必ず退避する**: `cp <file> <scratchpad>/<file>.bak`。取り消しは `git checkout` ではなくこのバックアップから戻す
- JSON/YAML等の構造化ファイルは、**全体再シリアライズの前に往復一致を検証する**（`json.dumps(load(raw))==raw` が真になる引数を先に特定する）。今回の正解は `indent=2, ensure_ascii=False, sort_keys=False, 末尾改行あり`
- 1〜2箇所の値変更は Edit ツールの行単位置換で行う。パーサを通さない
- **`.xcstrings` は Xcode がキーをソートしない**（プレフィックスでグループ化・グループ内のみ昇順）。この順序を壊すと差分が全面化する

## 2026-08-08 — JSONSnapshotStoreの日時はミリ秒精度＝同一ミリ秒内の2書き込みが等値になる

**症状**: `GoalStore.replace(goals:)` の新規Coreテスト「変更行のみ`updatedAt`更新」が稀に失敗。連続実行6回で1回再現するflaky。

**根本原因**: `JSONSnapshotStore` のエンコーダは日時をミリ秒精度で符号化する。テスト内の2回の書き込みが同一ミリ秒に収まると、更新前後の`updatedAt`が等値になり「更新された/されていない」の判定が偽装される。

**教訓**:
- Coreの永続化を跨いで日時の前後関係をアサートするテストは、**書き込み間隔を明示的に空ける**か、注入した固定Clockで時刻を進める
- 新規テストは1回のグリーンで完了とせず、**連続実行（最低5回）で安定を確認**してからマークする（今回この規律で捕捉できた）
